# 疎結合アーキテクチャの AWS サービス

## 概要

疎結合アーキテクチャでは、システム同士を直接強く依存させず、キュー、通知、イベント、メッセージブローカーを挟んで連携します。これにより、障害の波及を抑え、スケーリングしやすくなります。

| 目的 | 主なサービス |
|---|---|
| キューで非同期処理する | Amazon SQS |
| Pub/Sub で通知する | Amazon SNS |
| 既存 MQ 互換で連携する | Amazon MQ |
| イベント駆動で連携する | Amazon EventBridge |

## Amazon SQS

Amazon SQS は、メッセージキューを提供するサービスです。処理を依頼する側と処理する側の間にキューを置くことで、非同期処理と負荷平準化を実現します。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| キューイング | メッセージを一時的に保持する。 |
| 非同期処理 | 送信側と処理側を分離できる。 |
| スケーラブル | 大量メッセージを扱える。 |
| 標準 / FIFO | 高スループットの標準キューと順序制御の FIFO キューを選べる。 |
| デッドレターキュー | 処理失敗メッセージを隔離できる。 |

### 利用例

| シーン | 内容 |
|---|---|
| 注文処理 | 注文受付後、在庫確認やメール送信を非同期化する。 |
| 画像処理 | アップロードされた画像の変換処理をキューで分散する。 |
| バッチ連携 | 大量データを小さな処理単位に分けて処理する。 |
| 障害吸収 | 後続システムが一時停止してもメッセージを保持する。 |

### 向いている利用シーン

- 非同期処理を作りたい
- 処理側の負荷を平準化したい
- 一時的な障害でリクエストを失いたくない
- ワーカーを水平スケールさせたい

### 注意点

標準キューでは順序や重複処理に注意します。処理側は冪等性を持つ設計にするのが基本です。

## Amazon SNS

Amazon SNS は、Pub/Sub 型の通知サービスです。1 つのメッセージを複数の購読先に配信できます。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| Pub/Sub | Publisher が送ったメッセージを複数 Subscriber に配信する。 |
| 複数宛先 | SQS、Lambda、HTTP/S、メール、SMS などへ配信できる。 |
| ファンアウト | 1 つのイベントを複数処理へ分岐できる。 |
| FIFO トピック | 順序が必要な通知にも対応できる。 |

### 利用例

| シーン | 内容 |
|---|---|
| 通知配信 | 障害アラームをメールやチャット連携に送る。 |
| ファンアウト | 注文イベントを在庫、請求、通知処理に配信する。 |
| SQS 連携 | SNS から複数 SQS キューへ配信し、各システムが独立処理する。 |
| Lambda 起動 | イベント発生時に Lambda を起動する。 |

### 向いている利用シーン

- 1 つのイベントを複数宛先へ配信したい
- 通知やアラートを送りたい
- システム間を Pub/Sub で分離したい

### 注意点

SNS は基本的に配信サービスであり、キューのような長期的な処理待ち保持が主目的ではありません。処理側の耐障害性を高める場合は SNS + SQS の組み合わせがよく使われます。

## Amazon MQ

Amazon MQ は、Apache ActiveMQ や RabbitMQ をマネージドで提供するメッセージブローカーサービスです。既存の MQ プロトコルやアプリケーションを AWS に移行する時に使いやすいです。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| 互換性 | ActiveMQ / RabbitMQ と互換性がある。 |
| マネージド運用 | ブローカーの構築や運用を AWS が支援する。 |
| 既存アプリ移行 | JMS、AMQP、MQTT、STOMP など既存プロトコルを活かせる。 |
| 高可用性構成 | マルチ AZ 構成を選べる。 |

### 利用例

| シーン | 内容 |
|---|---|
| 既存 MQ 移行 | オンプレミスの ActiveMQ / RabbitMQ を AWS に移す。 |
| ハイブリッド連携 | 既存システムと AWS アプリを MQ 経由で接続する。 |
| プロトコル互換 | アプリ改修を抑えてクラウド移行する。 |

### 向いている利用シーン

- 既存アプリが ActiveMQ や RabbitMQ に依存している
- 標準プロトコル互換が必要
- SQS / SNS では置き換えにくい MQ 要件がある

### 注意点

新規クラウドネイティブ設計では、SQS、SNS、EventBridge の方が運用が簡単な場合があります。Amazon MQ は互換性重視の選択肢です。

## Amazon EventBridge

Amazon EventBridge は、イベントバスを使ってサービス間を疎結合に連携するサービスです。AWS サービス、SaaS、独自アプリケーションからのイベントを受け取り、条件に応じてターゲットへ配送します。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| イベント駆動 | 状態変化や操作をきっかけに処理を起動する。 |
| ルール | イベントパターンで配送先を制御できる。 |
| SaaS 連携 | 一部 SaaS のイベントも受け取れる。 |
| スケジュール | 定期実行にも使える。 |
| Schema Registry | イベント構造の管理に使える。 |

### 利用例

| シーン | 内容 |
|---|---|
| 注文イベント連携 | 注文作成イベントを複数マイクロサービスへ通知する。 |
| 運用自動化 | EC2 状態変更や Security Hub finding を処理する。 |
| SaaS 連携 | 外部 SaaS のイベントで AWS 側処理を起動する。 |
| 定期処理 | 毎時バッチや日次処理を起動する。 |

### 向いている利用シーン

- イベント駆動アーキテクチャを作りたい
- サービス間の依存を弱くしたい
- AWS サービスや SaaS のイベントを活用したい
- イベント内容で配送先を分けたい

### 注意点

EventBridge はキューではありません。処理側がメッセージを取りに行くモデルや、長時間保持、ワーカー制御が重要な場合は SQS も検討します。

## 使い分けの目安

| やりたいこと | 主な候補 |
|---|---|
| 処理をキューで待たせたい | SQS |
| 1 つの通知を複数に配信したい | SNS |
| ActiveMQ / RabbitMQ 互換が必要 | Amazon MQ |
| イベント内容に応じて連携したい | EventBridge |
| 複数システムに安全に分岐したい | SNS + SQS |
