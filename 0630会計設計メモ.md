以下の構成が、これまでの会話内容から見た一番バランスの良い設計です。

```txt
Next.js
  UI / 画面 / API client

Hono API
  認証 / 認可 / OpenAPI / DB操作 / ジョブ作成

PostgreSQL
  ユーザー・業務データ・ジョブ状態の正式保存

Redis + BullMQ
  重い処理のジョブキュー

document-worker
  Excel生成 / LibreOffice PDF変換 / S3保存

S3互換ストレージ
  生成されたExcel/PDF本体の保存
```

# 2. それぞれの責務

## Next.js

Next.jsは**フロントエンド専用**に寄せます。

担当すること:

```txt
- 画面表示
- フォーム入力
- Googleログインボタン
- API呼び出し
- PDF生成ジョブの作成
- ジョブ状態の表示
- 生成済みファイルへのリンク表示
```

担当しない方がいいこと:

```txt
- PrismaでDBを直接触る
- PDF生成処理
- LibreOffice実行
- 認可ロジックの本体
- 業務APIの実装
```

Next.js側は、OpenAPIから生成した型付きclientを使います。

```ts
import createClient from "openapi-fetch";
import type { paths } from "@/generated/api/schema";

export const apiClient = createClient<paths>({
  baseUrl: "/api",
  credentials: "include",
});
```

---

## Hono API

Hono APIは、アプリケーションの中心です。

担当すること:

```txt
- OpenAPI契約の定義
- Zodによる入力検証
- Better Authによる認証
- 認可チェック
- Prisma経由のDB操作
- PDF生成ジョブの作成
- Redis/BullMQへのジョブ投入
- ジョブ状態取得API
- S3 object keyの管理
```

外部から直接アクセスされるAPIは、基本的にこのHono APIだけにします。

```txt
Browser / Next.js
  ↓
Hono API
```

document-workerは外部公開しません。

---

## PostgreSQL

PostgreSQLは**正式な状態保存先**です。

保存するもの:

```txt
- User
- Session / Account
- 業務データ
- DocumentGenerationJob
- 生成済みファイルのobject key
- エラー情報
- ジョブの正式なstatus
```

Redisにもジョブ状態はありますが、アプリとして正式に表示・参照する状態はPostgreSQLに置きます。

```txt
Redis
  キュー処理上の状態

PostgreSQL
  アプリケーション上の正式状態
```

---

## Redis

Redisは、今回の構成では**ジョブキューの保存場所**です。

```txt
main-api
  ↓ job投入
Redis
  ↓ job待機
document-worker
  ↓ job取得
```

Redisを業務DBとして使うのではなく、**処理待ちの受付箱**として使います。

AWSで例えると、Redis + BullMQはだいたい以下に近いです。

```txt
Redis + BullMQ ≒ SQS + 軽いジョブ状態管理
PostgreSQL    ≒ RDS / DynamoDB
worker        ≒ ECS Task / Lambda
S3互換         ≒ S3
```

---

## BullMQ

BullMQは、Redisをジョブキューとして扱いやすくするNode.js/TypeScript向けライブラリです。

担当すること:

```txt
- ジョブ投入
- ジョブ取得
- 処理待ち管理
- retry
- backoff
- failed/completed管理
- concurrency制御
```

API側ではQueueを使います。

```ts
await documentQueue.add(
  "generate-document",
  {
    jobId: documentJob.id,
    templateId: input.templateId,
    data: input.data,
  },
  {
    attempts: 3,
    backoff: {
      type: "exponential",
      delay: 1000,
    },
  }
);
```

worker側ではWorkerを使います。

```ts
new Worker(
  "document-generation",
  async (job) => {
    const { jobId, templateId, data } = job.data;

    // Excel生成
    // PDF変換
    // S3保存
    // DB更新
  },
  {
    connection: {
      host: "redis",
      port: 6379,
    },
    concurrency: 1,
  }
);
```

LibreOffice変換は重いため、最初は `concurrency: 1` が安全です。

---

## document-worker

document-workerは、PDF/Excel生成専用の内部workerです。

担当すること:

```txt
- Redisからジョブを受け取る
- Excelテンプレートを読み込む
- 指定セルに値を入れる
- xlsxを保存する
- LibreOffice headlessでPDF変換する
- Excel/PDFをS3互換ストレージに保存する
- PostgreSQLのジョブ状態を更新する
```

担当しないこと:

```txt
- ユーザー認証
- 外部公開API
- フロントエンド向けレスポンス
```

認証・認可はmain-api側で済ませ、workerは信頼済み内部ジョブだけを処理します。

---

## S3互換ストレージ

生成ファイルの本体はPostgreSQLには保存せず、S3互換ストレージに保存します。

保存対象:

```txt
- 生成後のExcelファイル
- PDFファイル
```

DBにはobject keyだけ保存します。

```txt
PostgreSQL:
  excelObjectKey = generated/jobs/{jobId}/output.xlsx
  pdfObjectKey   = generated/jobs/{jobId}/output.pdf

S3:
  generated/jobs/{jobId}/output.xlsx
  generated/jobs/{jobId}/output.pdf
```

ローカルDockerではMinIO、本番や自宅サーバではGarageなども候補です。

## Caddyfile

```txt
:80 {
  handle_path /api/* {
    reverse_proxy api:8787
  }

  handle {
    reverse_proxy web:3000
  }
}
```

これにより、ブラウザからは以下のように見えます。

```txt
http://localhost/              → Next.js
http://localhost/api/*         → Hono API
http://localhost/api/auth/*    → Better Auth
http://localhost/api/openapi.json
```

Caddyを挟む理由は、**同一オリジンに見せるため**です。

```txt
http://localhost
  /      → web
  /api   → api
```

これにより、Cookie認証やCORSの複雑さを減らせます。

# 8. 処理順序

## PDF生成の流れ

```txt
1. ユーザーがNext.js画面で「PDF生成」を押す

2. Next.jsがPOST /api/document-jobsを呼ぶ

3. Hono APIがBetter Authで認証確認

4. Hono APIが認可確認
   例: このユーザーが対象団体・年度・書類を生成できるか

5. Hono APIがZodで入力検証

6. Hono APIがPostgreSQLにDocumentGenerationJobを作成
   status = queued

7. Hono APIがBullMQでRedisにジョブ投入

8. Hono APIがNext.jsへjobIdを返す

9. Next.jsはjobIdを持って状態表示画面に遷移

10. document-workerがRedisからジョブを取得

11. workerがDBのstatusをprocessingに更新

12. workerがExcelテンプレートを読み込む

13. workerが指定セルに値を挿入する

14. workerがxlsxを一時ディレクトリに保存する

15. workerがLibreOffice headlessでPDFへ変換する

16. workerがxlsx/pdfをS3互換ストレージに保存する

17. workerがPostgreSQLにobject keyを保存する
    status = completed

18. Next.jsがGET /api/document-jobs/{jobId}で状態確認

19. completedならPDF/Excelのキーやダウンロードリンクを表示
```

# 10. worker内部の処理設計

## worker全体

```ts
// document-worker/src/index.ts
import { Worker } from "bullmq";
import { processDocumentGenerationJob } from "./jobs/document-generation.job";

new Worker(
  "document-generation",
  async (job) => {
    await processDocumentGenerationJob(job.data);
  },
  {
    connection: {
      host: "redis",
      port: 6379,
    },
    concurrency: 1,
  }
);
```

## job処理

```ts
export async function processDocumentGenerationJob(input: {
  jobId: string;
  templateId: string;
  data: unknown;
}) {
  const workDir = await createWorkDir(input.jobId);

  try {
    await markJobProcessing(input.jobId);

    const xlsxPath = await fillExcelTemplate({
      templateId: input.templateId,
      data: input.data,
      workDir,
    });

    const pdfPath = await convertXlsxToPdf({
      xlsxPath,
      workDir,
    });

    const excelObjectKey = await uploadFileToS3({
      path: xlsxPath,
      key: `generated/document-jobs/${input.jobId}/output.xlsx`,
      contentType:
        "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
    });

    const pdfObjectKey = await uploadFileToS3({
      path: pdfPath,
      key: `generated/document-jobs/${input.jobId}/output.pdf`,
      contentType: "application/pdf",
    });

    await markJobCompleted({
      jobId: input.jobId,
      excelObjectKey,
      pdfObjectKey,
    });
  } catch (error) {
    await markJobFailed({
      jobId: input.jobId,
      error,
    });

    throw error;
  } finally {
    await cleanupWorkDir(workDir);
  }
}
```

# 12. S3 object key設計

おすすめはjobIdベースです。

```txt
generated/document-jobs/{jobId}/output.xlsx
generated/document-jobs/{jobId}/output.pdf
```

業務単位を含めるなら、

```txt
organizations/{organizationId}/documents/{jobId}/output.xlsx
organizations/{organizationId}/documents/{jobId}/output.pdf
```

ポイント:

```txt
- keyにjobIdを含める
- 冪等性を担保しやすい
- 同名ファイル衝突を避ける
- DBにはobject keyだけ保存
```

# 13. 同期処理ではなく非同期ジョブにする理由

PDF生成を同期APIでやるとこうなります。

```txt
POST /api/generate-pdf
  ↓
Excel生成
  ↓
PDF変換
  ↓
S3保存
  ↓
レスポンス
```

これは簡単ですが、以下の問題があります。

```txt
- APIが重くなる
- タイムアウトしやすい
- 同時実行に弱い
- LibreOfficeの失敗がAPI応答に直撃する
- retryしづらい
```

そのため、以下の非同期構成が良いです。

```txt
POST /api/document-jobs
  ↓
jobIdを返す

document-worker
  ↓
裏側でPDF生成

GET /api/document-jobs/{jobId}
  ↓
状態確認
```

---

# 14. OpenAPIに出すもの / 出さないもの

## OpenAPIに出すもの

```txt
- POST /api/document-jobs
- GET /api/document-jobs/{jobId}
- GET /api/workspaces
- POST /api/workspaces
- その他フロントから呼ぶ業務API
```

## OpenAPIに出さないもの

```txt
- document-worker内部処理
- Redis queueの内部payload
- LibreOffice実行API
- S3アップロード内部処理
```

workerは内部処理なので、公開API契約に含めなくて良いです。

ただし、main-apiとworkerで共有するjob payloadの型は、Zod schemaとして共有すると安全です。

# 15. 開発時の流れ

## API開発

```txt
1. api/src/schemas にZod schemaを書く
2. api/src/routes にHono routeを書く
3. OpenAPI response/requestを定義する
4. npm run generate:openapi
5. api/openapi.jsonを更新する
```

## フロント開発

```txt
1. npm run generate:api
2. web/src/generated/api/schema.d.tsを更新する
3. openapi-fetchでAPIを呼ぶ
4. 型エラーを見ながらUIを作る
```

## worker開発

```txt
1. sample JSONを作る
2. CLI的にExcel/PDF生成を検証する
3. S3保存を追加する
4. BullMQ Worker化する
5. DB status更新を追加する
```

最初はworkerをCLIとして動かせるようにすると、LibreOfficeやExcelテンプレートの検証が楽です。

```bash
pnpm start --template budget-request-v1 --input ./sample.json
```

# 16. 最終的な設計判断

今回の構成は、以下の目的に合っています。

```txt
- Next.jsとAPIを明確に分離したい
- APIはOpenAPIを契約にしたい
- フロントは生成型を使いたい
- 認証はBetter Authに寄せたい
- DBはPostgreSQL + Prismaにしたい
- PDF生成のような重い処理は通常APIから分離したい
- Docker Composeでローカル運用したい
- 将来的にAPIやworkerだけ別マシンに移せるようにしたい
```

最終構成を一言で言うと、

```txt
OpenAPI契約中心のHono API
+
Next.js frontend
+
PostgreSQL
+
Redis/BullMQ job queue
+
LibreOffice document worker
+
S3互換storage
```

です。

最初に実装するなら、順番は以下がおすすめです。

```txt
1. api + db + Better Authを作る
2. OpenAPI生成とweb側型生成を整える
3. document-jobs APIを作る
4. workerをCLIとして作る
5. MinIO/S3保存を追加する
6. Redis + BullMQで非同期化する
7. Next.jsからジョブ作成・状態表示を作る
```

この順番なら、認証・API契約・PDF生成・非同期処理を段階的に確認できます。
