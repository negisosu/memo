# アクセス管理・認証の AWS サービス

## 概要

アクセス管理・認証は、誰が、どの AWS リソースに、どの操作をできるかを制御する領域です。AWS では IAM を中心に、複数アカウント管理、フェデレーション、アプリケーションユーザー認証を組み合わせます。

| 目的 | 主なサービス |
|---|---|
| AWS リソースへの権限を管理する | AWS IAM |
| 一時的な権限を付与する | IAM Role |
| 権限定義を記述する | IAM Policy |
| 複数アカウントへ SSO する | AWS IAM Identity Center |
| 複数 AWS アカウントを管理する | AWS Organizations |
| アプリユーザーを認証する | Amazon Cognito |

## AWS IAM

AWS IAM は、AWS リソースへのアクセス権限を管理する中心的なサービスです。ユーザー、グループ、ロール、ポリシーを使って、操作できる範囲を制御します。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| 認証と認可 | AWS にアクセスする主体と権限を管理する。 |
| 最小権限 | 必要な操作だけを許可する設計が基本。 |
| グローバルサービス | リージョンに依存せず利用する。 |
| MFA 対応 | 重要なユーザーや操作に多要素認証を設定できる。 |
| 監査連携 | CloudTrail で API 操作履歴を追跡できる。 |

### 利用例

| シーン | 内容 |
|---|---|
| 管理者ユーザー | 管理者権限を持つユーザーを限定して作成する。 |
| 開発者権限 | 開発者に必要な EC2、S3、CloudWatch 権限だけを付与する。 |
| 運用者権限 | ログ閲覧や再起動など、運用作業に必要な権限だけを付与する。 |
| CI/CD 権限 | デプロイ用ロールに必要最小限の操作を許可する。 |

### 向いている利用シーン

- AWS リソースへのアクセス制御をしたい
- 操作できるサービスやアクションを制限したい
- ユーザーやアプリケーションに権限を付けたい
- 監査可能な権限管理をしたい

### 注意点

長期アクセスキーを人に配る運用は避け、可能な限りロールや一時認証情報を使います。root ユーザーは日常利用せず、MFA を必ず設定します。

## IAM Role

IAM Role は、一時的に引き受けられる権限のまとまりです。EC2、Lambda、ECS などの AWS サービスや、外部 ID プロバイダーからフェデレーションしたユーザーに権限を付与する時に使います。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| 一時認証情報 | 長期キーではなく期限付き認証情報を発行する。 |
| サービス連携 | EC2 や Lambda などの AWS サービスに権限を渡せる。 |
| クロスアカウント | 別アカウントのロールを引き受けて操作できる。 |
| 信頼ポリシー | 誰がそのロールを引き受けられるかを定義する。 |

### 利用例

| シーン | 内容 |
|---|---|
| EC2 から S3 へアクセス | EC2 に S3 読み取りロールを付ける。 |
| Lambda から DynamoDB へアクセス | Lambda 実行ロールに DynamoDB 操作権限を付与する。 |
| 管理アカウントから操作 | 運用担当者が各アカウントの管理ロールを引き受ける。 |
| GitHub Actions 連携 | OIDC で AWS ロールを引き受けてデプロイする。 |

### 向いている利用シーン

- AWS サービスに権限を付与したい
- アクセスキーを埋め込まずにアプリケーションを動かしたい
- 複数アカウントを安全に操作したい
- 外部 ID プロバイダーと連携したい

### 注意点

ロールには、権限ポリシーと信頼ポリシーの両方があります。権限が足りない場合だけでなく、引き受ける主体が信頼ポリシーに許可されていない場合も失敗します。

## IAM Policy

IAM Policy は、どのリソースに対して、どのアクションを、どの条件で許可または拒否するかを JSON で定義するルールです。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| JSON 定義 | Effect、Action、Resource、Condition などで権限を表す。 |
| アイデンティティベース | ユーザー、グループ、ロールに付ける。 |
| リソースベース | S3 バケットポリシーなど、リソース側に付ける。 |
| 明示的拒否 | Deny は Allow より優先される。 |
| 条件指定 | IP、MFA、タグ、時刻などで条件を絞れる。 |

### 利用例

| シーン | 内容 |
|---|---|
| S3 読み取り専用 | 特定バケットの GetObject だけを許可する。 |
| MFA 必須 | MFA を使っている場合だけ重要操作を許可する。 |
| タグベース制御 | Project タグが一致するリソースだけ操作を許可する。 |
| IP 制限 | 社内 IP からの操作だけを許可する。 |

### 向いている利用シーン

- 権限を細かく制御したい
- 最小権限を実現したい
- 条件付きでアクセスを許可したい
- 複数ユーザーに同じ権限セットを適用したい

### 注意点

ワイルドカードの多用は避けます。`Action: *` や `Resource: *` は便利ですが、過剰権限になりやすいです。

## AWS IAM Identity Center

AWS IAM Identity Center は、複数 AWS アカウントやアプリケーションへのシングルサインオンを提供するサービスです。旧 AWS Single Sign-On です。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| SSO | 1 回のログインで複数アカウントへアクセスできる。 |
| 権限セット | アカウントごとの権限を Permission Set として管理する。 |
| 外部 IdP 連携 | Microsoft Entra ID、Okta などと連携できる。 |
| Organizations 連携 | 複数アカウントへの割り当てを管理しやすい。 |

### 利用例

| シーン | 内容 |
|---|---|
| 複数アカウントログイン | 開発、本番、監査アカウントに同じポータルからアクセスする。 |
| 職務別権限 | 管理者、開発者、閲覧者の権限セットを作る。 |
| 退職者対応 | 社内 IdP のユーザー停止で AWS アクセスも止める。 |
| 一時的な権限付与 | プロジェクト期間だけ特定アカウントへアクセスを許可する。 |

### 向いている利用シーン

- 複数 AWS アカウントを使っている
- 人間のログインを一元管理したい
- 社内 ID 基盤と AWS を連携したい
- IAM ユーザーを増やしたくない

### 注意点

IAM Identity Center は人のログイン管理に向いています。アプリケーションや AWS サービスの実行権限には IAM Role を使うのが基本です。

## AWS Organizations

AWS Organizations は、複数の AWS アカウントを組織としてまとめて管理するサービスです。OU、SCP、統合請求などを使って、アカウント単位の管理をしやすくします。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| アカウント管理 | 複数アカウントを組織単位で管理できる。 |
| OU | 本番、開発、セキュリティなどの単位で階層化できる。 |
| SCP | アカウントに対する最大権限の境界を設定できる。 |
| 統合請求 | 複数アカウントの請求をまとめられる。 |
| サービス連携 | IAM Identity Center、CloudTrail、Config などと連携する。 |

### 利用例

| シーン | 内容 |
|---|---|
| 環境分離 | 本番、開発、検証を別アカウントに分ける。 |
| セキュリティ統制 | 本番 OU で特定リージョンの利用を禁止する。 |
| ログ集約 | 監査アカウントに CloudTrail ログを集約する。 |
| 請求管理 | 部門別アカウントをまとめて請求管理する。 |

### 向いている利用シーン

- 複数アカウントを標準化したい
- アカウントごとに責任範囲を分けたい
- 組織全体の制約をかけたい
- 請求や監査を一元化したい

### 注意点

SCP は権限を付与するものではなく、アカウント内で許可できる最大範囲を制限するものです。IAM ポリシーで Allow されていても、SCP で Deny されていれば実行できません。

## Amazon Cognito

Amazon Cognito は、Web アプリやモバイルアプリのユーザー認証、サインアップ、サインイン、フェデレーションを提供するサービスです。

### 主な特徴

| 特徴 | 説明 |
|---|---|
| ユーザープール | アプリユーザーの登録、認証、MFA などを管理する。 |
| ID プール | 認証済みユーザーに AWS 一時認証情報を渡せる。 |
| フェデレーション | Google、Apple、SAML、OIDC などと連携できる。 |
| トークン発行 | JWT を使ってアプリケーション認証を行う。 |

### 利用例

| シーン | 内容 |
|---|---|
| 会員ログイン | Web サービスのユーザー登録とログインを実装する。 |
| ソーシャルログイン | Google や Apple アカウントでログインできるようにする。 |
| API 認証 | API Gateway と組み合わせて JWT 認証を行う。 |
| モバイルアプリ | アプリユーザーに S3 アップロード権限などを一時的に渡す。 |

### 向いている利用シーン

- アプリケーションのエンドユーザー認証を作りたい
- 自前で認証基盤を持ちたくない
- API Gateway や Lambda と連携したい
- SNS ログインや企業 IdP 連携を使いたい

### 注意点

Cognito は AWS 管理者向けの IAM とは役割が異なります。IAM は AWS リソース操作の権限管理、Cognito はアプリケーション利用者の認証に使います。

## 使い分けの目安

| やりたいこと | 主な候補 |
|---|---|
| AWS 操作権限を管理したい | AWS IAM |
| EC2 や Lambda に権限を渡したい | IAM Role |
| 権限ルールを細かく定義したい | IAM Policy |
| 複数アカウントへ SSO したい | IAM Identity Center |
| 複数 AWS アカウントを統制したい | AWS Organizations |
| アプリユーザーのログインを作りたい | Amazon Cognito |
